Основания по пунктам:

1. Смысл свежести определён: последние стабильные версии инструментов, наиболее свежие Python-зависимости в рамках официальных ограничений совместимости; объявленная, но недоступная версия расширения не выдаётся за установленную. Область ограничена инструментом начальной настройки, без непрошеного обновления продуктовых зависимостей GRAF.
2. Явный отказ, закреплённый режим и проверка завершённой рабочей копии определены отдельно от обновления. Обновление не должно происходить посреди чужой работы. Это соответствует запросу о свежести и сохраняет возможность воспроизводимого контроля.
3. Требования явно сохраняют конфигурацию, локальные правки, проектные шаблоны и пользовательские данные; запрещают общую принудительную перезапись и требуют штатного отката и передачи ошибок.
4. Критерии требуют реального повышения версии при сочетании установленной 1.0.0, доступной встроенной 1.0.1 и объявленной 1.0.2, сохранности конфигурации, повторного разрешения Python-зависимостей, Ponytail и нового/существующего GRAF. CONTRIBUTING.md требует изоляции от домашнего каталога и состояния разработчика, проверок macOS/Ubuntu, свежих upstream-версий и опубликованного артефакта. Достаточно для начала реализации; это описание обязательных проверок, не утверждение, что существующие тесты уже их выполняют.

Обнаруженные ограничения текущих проверок, которые исполнитель обязан устранить:

- tests/extension-update-live.py занижает только agent-context и не воспроизводит пропуск git 1.0.0 → 1.0.1. После изменения нужен фактический тест git, версии и сохранённых конфигураций.
- tests/smoke-live.sh безусловно выставляет SPECKIT_PONYTAIL=0; поэтому существующая задача latest-ponytail, передающая 1, не доказывает реальную установку Ponytail. Проверка должна сохранять явный выбор задачи и подтверждать установленную версию/источник плагина.
- Полная изоляция проверки подразумевает не только временный HOME: унаследованные CODEX_HOME, UV_TOOL_DIR и UV_TOOL_BIN_DIR также должны направляться во временную область.
- Не выполнено ни одной функциональной или выпускной проверки этим проверяющим. Общие библиотеки обновляются до совместимых версий; максимальный номер на PyPI сам по себе не критерий совместимости.
- Ponytail — общая установка Codex. Закреплённая старая рабочая копия после обновления общего плагина может потребовать явного обновления; нельзя объявлять её прежнюю точную проверку успешной без подтверждения.

Перечитанный итог checklist: checked=4, unchecked=0. Изменены только состояние checklist и этот отчёт. Код, Git/GitHub, коммиты, релизы, установки и окружение не менялись.

## Независимая проверка реализации до выпуска

Проверен текущий diff без изменения кода. Адаптация обновления вызывает штатную точку входа Specify, сохраняет штатную транзакцию, передаёт конечный ввод и код завершения. Подмена доступной версии ограничена двумя официальными встроенными расширениями, разрешённым каталогом без отдельного download_url и официальным repository. Изменение install_cli сохраняет быстрый путь только для --frozen и использует --upgrade для обычного обновления. Разрешение Issue Canon привязано к стабильному тегу и его каталогу. Явная изоляция HOME/CODEX_HOME/UV_TOOL_DIR/UV_TOOL_BIN_DIR и проверка реальной установки Ponytail добавлены. В добавленной оболочечной логике несовместимых с Bash 3.2 конструкций не найдено.

Два замечания P2 перед завершением проверки:

1. integrations/codex-worktree.sh передаёт --with-ponytail безусловно. Этот аргумент переопределяет SPECKIT_PONYTAIL=0, поэтому явный отказ через документированную переменную в поставляемом hook не сохраняется. Установщик уже включает Ponytail по умолчанию: достаточно использовать его обычный выбор либо явно сохранять отрицательное значение. Нужна проверка hook с заданным SPECKIT_PONYTAIL=0.
2. available_info корректирует версию только когда встроенная версия ниже версии каталога. Обратное рассогласование оставляет устаревшее расширение: установленная 1.0.0, каталог 1.0.0, встроенная 1.0.1 приводит в штатном discover_updates к Up to date до рассмотрения встроенной версии. Для этих же разрешённых официальных bundled-источников доступная версия должна отражать фактически поставляемую; отдельное сообщение о недоступной версии нужно только когда каталог новее. Нужна проверка отстающего каталога.

Требования остаются подтверждёнными: checked=4, unchecked=0. Замечания относятся к реализации, не к ясности требований. Функциональные и выпускные проверки исполнителя ещё завершаются; готовность к выпуску не подтверждена. Изменён только этот отчёт.

## Проверка нормализации manifest после первой установки

Последняя правка проверена отдельно: после capture_project_dependency_state и capture_project_skills_state создаётся новый lock, затем вызывается уже существующий prepare_codex_skill_refresh. Поэтому хеши сгенерированных upstream-файлов заменяются на хеши окончательных проверенных bootstrap overlays сразу в первой установке. Нормализация изменяет только .specify/integrations/codex.manifest.json, не payload навыков, расширения, общий инфраструктурный код или lock. Сам manifest не входит в project_skills и не создаёт циклической зависимости хешей.

Проверки безопасности сохранены: старый lock и локальные изменения проверяются до установки; повторный вызов сверяет актуальные навыки с уже новым lock, отказывает при несовпадении, запрещает символьные ссылки и неуправляемые пути, требует непустой корректный manifest и записывает его атомарно. Ошибка передаётся через || return 1 до итогового doctor/ready. Для FROZEN=1 функция возвращает сразу, поэтому закреплённый режим не получает новой мутации. Новых несовместимых с Bash 3.2 конструкций не добавлено.

Новый smoke assert расположен сразу после первой установки и сверяет каждое значение manifest с реальным SHA-256 файла; он проверяет обнаруженную причину дрейфа, а не только код завершения. Отдельная проверка полного повторного состояния GRAF нужна, чтобы подтвердить сохранность остальных файлов.

Замечаний к этой правке по текущему коду нет. Сообщение исполнителя о прошедшей проверке hook принято как контекст, без самостоятельного утверждения её полного результата. Прежний успешный GitHub canary привязан к предыдущему коммиту и не считается доказательством для новой правки: обязательны новые точные SHA-проверки и завершённые функциональные/выпускные ворота. Checklist перечитан: checked=4, unchecked=0. Проверяющий изменил только этот отчёт.
